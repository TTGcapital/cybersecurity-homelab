# Project 04 — SSH Logging and Failed-Login Detection

## Objective

Use Ubuntu's system logs to investigate SSH authentication activity, identify repeated failed logins, and convert the manual investigation into a reusable reporting script.

## Environment

| System | Role | Lab address |
|---|---|---:|
| Kali Linux | Administrative and test workstation | `192.168.1.100` |
| Ubuntu `lab-srv01` | SSH server and log source | `192.168.1.10` |
| pfSense | Isolated LAN gateway | `192.168.1.1` |

All activity occurred inside the authorised, offline `192.168.1.0/24` homelab.

## Investigation

Successful SSH activity was reviewed with:

```bash
sudo journalctl -u ssh --since "2 hours ago" --no-pager
```

The logs confirmed successful sessions for the lab accounts `aisha` and `omar`, both originating from the Kali workstation.

A controlled authentication incident was then generated by attempting to sign in to `aisha` with an incorrect password twice. The server-side evidence was filtered with:

```bash
sudo journalctl -u ssh --since "10 minutes ago" --no-pager |
grep -E "Failed password|authentication failure|Accepted password"
```

## Observed result

| Field | Value |
|---|---|
| Target account | `aisha` |
| Source address | `192.168.1.100` |
| Failed attempts | 2 |
| Service | SSH |
| Outcome | Rejected; no authenticated session opened |

A compact command converted the raw events into an analyst-friendly summary:

```text
2 user=aisha source=192.168.1.100
```

The source address identifies the system that initiated the connection—in this controlled test, Kali—not automatically the human operating it.

## Automation

The reusable script at [`scripts/ssh-failure-report.sh`](../../scripts/ssh-failure-report.sh) groups failures by target account and source IP over the previous 24 hours. It accepts an optional alert threshold, defaulting to three attempts.

```bash
sudo ./scripts/ssh-failure-report.sh
sudo ./scripts/ssh-failure-report.sh 2
```

Verified outputs for the controlled two-attempt test were:

```text
[INFO] attempts=2 user=aisha source=192.168.1.100
[ALERT] attempts=2 user=aisha source=192.168.1.100
```

The first used the default threshold of three; the second used a threshold of two.

## Security considerations

- Authentication logs can contain usernames, internal addresses, timestamps and other operational details.
- A source IP is an investigation lead, not conclusive attribution to a person.
- Alert thresholds need tuning because normal user mistakes can generate failures.
- This script reports evidence but does not block traffic or replace a SIEM.
- No passwords, public IP addresses, keys or personal information are included here.

## What I learned

- How to investigate successful and failed SSH authentication with `journalctl`
- How to extract useful fields from raw logs using `grep`, `sed`, `sort`, `uniq` and `awk`
- How to distinguish an authentication attempt from an authenticated session
- Why IP evidence must be interpreted carefully
- How to turn a manual security check into a parameterised Bash tool
